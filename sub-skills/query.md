# 查询能力

## 能力定位

处理“我想找什么权益”的标准查询链路。主 `SKILL.md` 已完成场景路由，本文件不再判断 query/detail/recommend/more。

## 依赖

按顺序读取：

1. `_shared.md`：脚本、配置、公共响应和会话状态。
2. `api/offer-query.md`：查询接口的请求/响应字段和脚本调用示例。
3. `result-template.md`：通用响应和用户展示建议。
4. `config/tags.txt`、`config/regions.txt`、`config/banks.txt`：首次进入查询能力时完整读取；同一会话内如果字典未变化，直接复用会话中的已加载内容。

## 用户可见进度规则

允许输出简短的泛化阶段提示，例如“正在分析您的意图”“正在匹配权益”“正在解析权益数据”“正在整理推荐结果”。进度提示不得编号，不得展开内部步骤，不得包含任何业务细节。

进度提示禁止包含：标签值、标签数量、`matchScore`、银行或地区名称、别名转换、请求 JSON、`filters`、事件 ID、文件路径、原始响应、脚本退出码、工具调用信息，以及 `<HOOK_INSTRUCTION>`、`<EnvironmentContext>` 等宿主上下文。

完成接口调用、响应解析、上下文保存后，再输出最终 Markdown 结果；用户未要求调试时，不输出内部参数和中间结果。

## 查询解析

本能力直接完成用户需求到查询请求的转换，不再依赖独立的解析文件。

### 全量输入

- 用户原始需求；
- 完整 `config/tags.txt`：受控标签及描述；
- 完整 `config/regions.txt`：支持地区字典；
- 完整 `config/banks.txt`：银行标准名和别名；
- 当前对话上下文中的日期、银行、地区和其他明确事实。

本地模型需要把三个字典作为同一次意图分析的完整参考输入：

- 标签字典用于比较用户意图与全部候选标签的关联度；
- 地区字典用于识别地区事实和判断是否需要提示；
- 银行字典用于把用户说法转换为 `filters.banks` 的标准名。

这些字典只提供给本地模型，不新增请求字段，也不把整份字典发送给 EverySkill 接口。

### 标签分析规则

1. 将用户需求与**全部标签字典**逐项比较，不只按关键词命中一个标签。
2. 识别直接主题、同类主题、上下位主题和弱关联主题，按关联度排序。
3. 标签数量以 3~5 个为优先目标；用户表达不足时可以少于 3 个，不得为了凑数添加无关标签；最多不超过 10 个。
4. `matchScore` 使用以下区间：
   - `1~30`：轻度、宽泛或弱关联；
   - `31~60`：中度、同类或场景关联；
   - `61~100`：强度、明确或精确关联。
5. 只有当前 `config/tags.txt` 中存在的标签名才能进入 `intentTags`；无法映射的主题不创建新标签。
6. “万事达”“信用卡”、发卡银行、卡等级、地区、时间和达标门槛属于上下文或事实，不要自动当成语义标签。
7. 银行别名转换为 `filters.banks` 的标准名；用户未提银行时不发送 `banks`。
8. 地区写入 `filters.regions`；不在地区字典时只生成内部提示，不阻断请求。
9. 时间统一为 `yyyy-MM-dd`；无法确定时先向用户澄清，不猜日期。
10. 没有事实过滤条件时，`filters` 使用 `null`。

### 输出格式

只生成 query 请求 JSON，不输出 route、Markdown、标签分析过程或额外解释：

```json
{
  "intentTags": [
    {"tagName":"主题标签A","matchScore":85},
    {"tagName":"主题标签B","matchScore":55},
    {"tagName":"主题标签C","matchScore":25}
  ],
  "filters": {
    "banks":["ABC"],
    "regions":["香港"],
    "timeRange":{"start":"2026-10-01","end":"2026-12-31"}
  }
}
```

如果用户没有事实过滤条件：

```json
{"intentTags":[{"tagName":"主题标签A","matchScore":85}],"filters":null}
```

## 用户输出边界

意图分析、标签选择、银行归一化、地区判断和请求组装都在本地静默完成。不要向用户输出：

- `intentTags`、`matchScore` 或标签候选列表；
- 银行别名转换过程；
- `filters` 请求 JSON；
- “正在解析标签”“正在匹配参数”等内部步骤文本。

只在最终响应中展示真实 Offer 和必要的适用条件。

## 处理流程

1. 完成全量字典意图分析，生成只包含 `intentTags` 和 `filters` 的 JSON。
2. 按 `api/offer-query.md` 的 POSIX 或 PowerShell 示例调用 `api-call`，并为本次调用生成事件 ID。
3. 根据脚本返回的 `RESPONSE_FILE` 读取原始响应，不依赖聊天窗口中是否保留脚本输出。
4. 检查脚本退出码和顶层 `code`；失败时按错误码提示，不读取不存在的 `data`。
5. 成功时保存 `queryCacheId`、原始 `intentTags`、原始 `filters` 和分页状态到会话上下文。
6. 用 `result-template.md` 生成 Markdown 最终回复。
7. 用户要求更多时切换到 `more.md`，复用已保存的原始条件，不重新解析原始需求。
8. 上下文保存并完成回复后，按事件 ID清理请求/响应临时文件。

## 不允许

- 不直接调用 curl。
- 不传自然语言 query 字段。
- 不创造 `config/tags.txt` 中不存在的标签。
- 不展示内部匹配得分或标签分析过程。
- 不对服务端返回列表重新排序。
