# 查询能力

处理“我想找什么权益”。场景路由已由 `SKILL.md` 完成，本文件不再判断 query/detail/recommend/more。

## 依赖

进入本能力后，**在同一轮里一次性读完**下面这些文件（并行读取，不要读一个、想一步、再读下一个）：

| 文件 | 用途 |
|---|---|
| `common.md` | 脚本调用、响应判定、会话状态、清理 |
| `api/offer-query.md` | 请求/响应字段 |
| `result.md` | 列表展示 |
| `config/client.conf` | 接口地址和路径 |
| `config/tags.txt`、`regions.txt`、`banks.txt` | 字典（判断“查询词还是标签”要对照标签字典；只给本地模型参考，不发送给服务端） |

同会话里已经读过且没变的文件不用重读（字典尤其如此）。

## 总流程

```text
⓪ 对照上一轮：延续还是换话题（仅多轮对话）  →  ① 提取并合并事实条件 filters
→ ② 判定主题：查询词 / 标签 / 无主题  →  ③ 生成主题参数
→ ④ 直接把 JSON 写进脚本命令并调用  →  ⑤ 保存会话状态  →  ⑥ 展示结果
```

整个处理过程静默完成：意图分析、标签选择、银行归一化、请求组装、调用、保存状态都不输出文字，只在最后给出一条回复（阶段提示和输出边界见 `SKILL.md` 的“用户可见输出”）。

## ⓪ 条件继承（多轮对话）

**最新消息为主，历史只作参考。** 最新消息里明说的条件一律覆盖历史；没提到的维度，按语义判断留不留。历史来自会话状态里“上一轮生效的条件”（见 `common.md`）；没有上一轮（首次提问）就跳过本节。

### 先判断：延续、换话题还是重置

把最新这句话**单独**拿出来看，能不能独立成立：

| 判断 | 信号 | 主题怎么处理 |
|---|---|---|
| **延续** | 单看缺主题，或带指代、增补词：“这些”“其中”“还有吗”“只要”“换成”“再加”“也”“便宜点” | 沿用上一轮的主题（`searchInfo` 或 `intentTags`） |
| **换话题** | 自带新的品牌或主题，和上一轮不是一类 | 替换为新主题；查询词和标签二选一，也随之整体替换（上轮是查询词、这轮是品类，查询词就丢弃） |
| **重置** | “重新来”“都不限”“换个思路” | 清空主题、地区、时间 |

**拿不准就按“换话题”处理**：误丢条件只会让结果变宽，用户补一句就行；误带条件会让结果悄悄变窄甚至落到兜底，用户很难发现。

### 各维度保留规则

| 维度 | 延续 | 换话题 | 用户明说时 |
|---|---|---|---|
| 主题 | 沿用 | 替换 | — |
| 银行 | 保留 | **保留**（这是用户身份，如“我是工行卡”） | 改成新银行，或说“不限银行”则清除 |
| 地区 | 保留 | **丢弃**（除非最新消息自己给了） | 新地区覆盖；“不限地区”清除 |
| 时间 | 保留，相对说法（“下个月”）按当前日期重新换算，已过期的丢弃 | **丢弃** | 新时间覆盖；“不限时间”清除 |

重置只清空主题、地区、时间；银行只在用户明说时才清除。

### 其他规则

- **合并后发送完整请求**（主题 + 全部 `filters`），不是只发增量。
- **服务端没有“排除”条件**：“不要香港的”只能在 `regions.txt` 里改选其余地区；选不出来就如实说做不到，不要硬造条件。
- **分页不走本节**：“更多”冻结首次条件（见 `more.md`）。用户后来新说的条件要重新发起一次 query，而不是塞进分页请求。
- **回复里点明实际生效的沿用条件**，让用户有机会纠正，例如“仍按香港、工行卡为您查找”。换话题时丢弃的条件不用提。展示方式见 `result.md`。

## ① 事实条件（filters）

三种主题方式共用，查询词和标签都只负责“找什么”，`filters` 是门槛，结果必须同时满足。下面是从最新消息提取的规则，提取后再按 ⓪ 与历史合并。

- **银行**：按 `banks.txt` 把用户说法转成标准名，写入 `banks`；用户没提就不带。
- **地区**：写入 `regions`；不在 `regions.txt` 里也照常发送，结果有就照常展示（字典仅作提示，不阻断）。回复里最多提示一句“目前可能不支持该地区”，**不要断言“不支持”“未覆盖”**，也不要因此不发请求、不展示结果。
- **时间**：统一 `yyyy-MM-dd`，相对说法（“下个月”“国庆”）按当前对话日期换算；无法确定时先向用户澄清，不猜日期。
- “万事达”“信用卡”、卡等级、达标门槛是上下文，不是条件，也不是标签。
- 没有任何事实条件时 `filters` 为 `null`。

## ② 判定主题（命中即停）

**默认走标签，查询词是例外。** 按顺序判断：

| 顺序 | 条件 | 走法 |
|---|---|---|
| 1 | 用户点名了**具体对象**（品牌、商户、固定写法的优惠模式或具体权益名），语义确定，且标签字典里**没有**对应标签 | **查询词** `searchInfo` |
| 2 | 能映射到标签字典：品类、场景、主题、宽泛需求，以及字典里本来就有同名标签的专名 | **意图标签** `intentTags` |
| 3 | 以上都不是（只有条件，或什么都没说） | **无主题**：`intentTags` 为空，只带 `filters` |

“语义确定”要同时满足：① 是专有名称或固定说法，不是普通名词；② 一看就知道指谁、指什么，没有指代、省略或模糊词；③ 能压成一个 2~6 字的核心词。任何一条不满足，就不生成查询词，往下一行判断。

| 用户说 | 判定 | 结果 |
|---|---|---|
| 星巴克有什么优惠 | 1：品牌，无对应标签 | 查询词 `星巴克` |
| 万豪的权益 / 找找海底捞 | 1：品牌 | 查询词 `万豪` / `海底捞` |
| 有没有买一送一的 | 1：固定写法的优惠模式 | 查询词 `买一送一` |
| 香港星巴克，工行卡 | 1 + 条件 | 查询词 `星巴克`，`regions`=香港，`banks`=ICBC |
| 星巴克的下午茶 | 1：对象是星巴克，标签表达不了“谁” | 查询词 `星巴克`（下午茶丢弃） |
| 想去泡温泉 / 周末带孩子玩 | 2：场景、主题 | 标签 |
| 有没有下午茶券 | 2：字典有“下午茶” | 标签 `下午茶` |
| 迪士尼门票 / 海洋公园 | 2：字典有同名标签 | 标签 `迪士尼乐园` / `海洋公园` |
| 酒店优惠、咖啡、海鲜 | 2：品类 | 标签 |
| 有什么折扣 / 打折的 | 2：泛称，写法不固定 | 标签 `购物折扣`（低分） |
| 那家咖啡店 / 上次那个 | 指代不明：先用会话里已展示的 Offer 确认商户；确认不了 | 标签 `咖啡甜点` |
| 香港好吃的 / 带孩子去哪玩（没提“权益”） | 2：消费场景也是主题，需求宽泛 | `餐饮美食` 较高分（约 70）+ 少量低分相邻标签，`regions`=香港 / 标签 `亲子` 等 |
| 香港有什么优惠 | 3：只有条件 | 无主题，`regions`=香港 |
| 有什么好的推荐 | 3：什么都没说 | 无主题，`filters` 为 `null` |

**查询词不是用来“多找一些”的**：它只匹配名称或商户里包含该词的权益，范围窄且不理解语义。拿不准就走标签。

## ③ 生成主题参数

### 查询词（`searchInfo`）

1. **取核心名称**：去掉地区、银行、时间（它们进 `filters`），去掉品类泛词（酒店、餐厅、咖啡店、门票、券）、泛称（优惠、权益、活动）、店铺后缀（店、分店、旗舰店、官方）以及语气词（“有没有”“帮我找”“的”）。例：“星巴克咖啡店”→`星巴克`，“万豪酒店的优惠”→`万豪`。
2. **越短越稳**：服务端按“名称或商户**包含**该词”做子串匹配，不分词、不理解同义词，也不支持多个词、空格拼接、“或”、通配符；目标 2~6 字，上限 20 字。
   词里的引号、反引号、`$`、反斜杠、分号、竖线、`&`、换行等特殊字符一律去掉（会破坏脚本命令，见 `common.md` 的“引号安全”）。
3. **只传一个词**：用户提到多个对象时取最先、最重点的一个，其余在回复里建议分开查。
4. **原样书写**：用户写中文就用中文，写英文就用英文（不区分大小写）；不翻译、不扩写同义词或别称、不纠错猜测。
5. **优惠模式只在写法固定时生成**（买一送一、早鸟、双人套餐、积分翻倍）；折扣、满减、返现这类泛称不算模式，走标签。
6. 生成了查询词就**不再生成** `intentTags`。

### 意图标签（`intentTags`）

1. 把用户需求与**全部**标签逐项比较，不是关键词命中一个就停；识别直接主题、同类主题、上下位主题和弱关联主题，按关联度排序。
2. 优先 3~5 个；用户表达不足时可以更少，不为凑数添加无关标签；最多 10 个。
3. `matchScore`：`1~30` 轻度/宽泛，`31~60` 中度/同类，`61~100` 强/明确。
4. 只能用当前 `tags.txt` 里存在的标签名；映射不了的主题不创建新标签。
5. **分数反映“用户说了多少”，不是你对城市或场景的联想**：
   - 需求宽泛（“好吃的”“好玩的”“住哪”）时，高分给宽泛标签（如 `餐饮美食`、`旅游出行`），具体品类标签只给低分，或干脆不选。
   - 不要把地区联想成地方特色品类（“香港”≠`港式茶餐厅`）；地区是 `filters`，不是主题。
   - 只有用户明确说到的具体品类（“想吃海鲜”“要下午茶”）才给具体标签高分。

### 无主题

`intentTags` 为空数组，只带 `filters`。服务端返回随机参考推荐（`isDefault=true`，不受条件约束），展示话术见 `result.md`。

## ④ 请求 JSON 的格式

请求 JSON **不在回复里写出来**：不展示、不复述、不先起草再抄，直接作为 `--data` 参数写进脚本命令（见 `common.md` 的“调用模板”）。下面只是格式示例。

```json
{"searchInfo":"星巴克","filters":{"regions":["香港"]}}
```

```json
{"intentTags":[{"tagName":"温泉度假","matchScore":85},{"tagName":"亲子","matchScore":55}],
 "filters":{"banks":["ABC"],"regions":["香港"],"timeRange":{"start":"2026-10-01","end":"2026-12-31"}}}
```

```json
{"intentTags":[],"filters":{"regions":["香港"]}}
```

`searchInfo` 和 `intentTags` 二选一，不同时出现；没有主题时 `intentTags` 为空数组、不带 `searchInfo`。

## 场景分支

| 场景 | 做法 |
|---|---|
| 首次提出需求 | 按 ①②③ 全流程 |
| 多轮中追加、修改条件或换话题（“只要香港的”“换成工行卡”“再看看餐厅”） | 先按 ⓪ 合并条件，再走 ②③；**一律重新发起一次 query**，不是 more |
| 只有条件、没有主题 / 什么都没说 | 无主题方式调用，不追问，不编造主题；回复里顺带引导用户说出想找的类型或品牌 |
| 时间等关键条件含糊 | 先问清楚再调用 |
| 查询词查不到（`isDefault=true`） | **不自动换词重试**；按 `result.md` 说明没找到，并建议换个说法，或描述想要的类型（用户同意后改走标签） |

## ⑤⑥ 调用、保存与展示

1. 按 `api/offer-query.md` 的请求字段，把 JSON 直接写进 `common.md` “调用模板”的 `--data` 参数调用，请求 ID 前缀 `query-`。
2. 读取 `RESPONSE_FILE`，按 `common.md` 的响应判定处理。
3. 成功后把 `queryCacheId`、**合并后实际发送的** `searchInfo` 或 `intentTags` 和 `filters`（并标明其中哪些是沿用的）、分页状态和已展示 Offer 存入会话状态。
4. 按 `result.md` 生成最终回复；用户要更多时转 `more.md`，复用已保存的原始条件，不重新解析原始需求。
5. 保存并回复完成后清理临时文件。

## 不允许

- 不直接调用 curl。
- 不传自然语言整句；`searchInfo` 只放提取后的精简核心词。
- 不同时传 `searchInfo` 和 `intentTags`。
- 不创造 `tags.txt` 里没有的标签。
- 不展示内部匹配得分、标签分析过程和请求参数。
- 不对服务端返回的列表重新排序。
